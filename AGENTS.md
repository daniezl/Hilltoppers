# Working on Hilltoppers with an AI agent

This file is for coding agents (Cursor, Copilot, Codex, Claude Code, ...) and
for the people prompting them. Read it before changing anything.

**Who you are working for.** The person asking for a change is most likely a
student who uses the extension every day and has never written code. Assume
they cannot read a diff. Explain in plain words, show them a picture, and when
a request could mean two different things, ask one short question instead of
guessing.

## What this project is

A Chrome extension (and an iOS app, not covered here) for students at
Saint Johnsbury Academy (SJA). It answers three questions: what block is it right now and
how long is left, what does the rest of today look like, and what is for lunch.
The toolbar icon shows the minutes left in the current block.

That sentence is also the boundary. A change that helps answer those questions
is welcome. Anything else — new tabs, social features, things unrelated to the
school day — should start as a GitHub issue, not a pull request. The extension
stays small on purpose.

## Where things are

Everything for the extension lives in `chrome-extension/`. Most changes touch
one folder.

| Path | What it is |
|---|---|
| `src/popup/Popup.tsx`, `popup.css` | The main window. Today's blocks, the countdown, the lunch menu, the footer |
| `src/background/background.ts` | Service worker. Draws the toolbar icon, refreshes the schedule on alarms |
| `src/classSettings/` | The "Class settings" page: the user's class names, which blocks show on Green vs White days |
| `src/options/`, `src/feedback/`, `src/login/` | Other extension pages. Each is `<name>.html` at the root + a folder in `src/` |
| `src/services/` | Fetching: schedule (`scheduleService.ts`), day type (`dayTypeResolver.ts`), menu (`diningMenuService.ts`), feedback |
| `src/storage/` | User preferences. `blockPreferences.ts` (per-block settings), `schedulePreferences.ts` (time format, lunch, grad year). Saved to `chrome.storage.sync`, mirrored to Firestore when signed in |
| `public/schedule/*.json` | The bell schedules: `schedule_mon_thu`, `schedule_wed`, `schedule_fri`, `late_start`, `abdec`. Hand-edited |
| `manifest.json` | Chrome manifest. Permissions and version live here |
| `../data/public/*.json` | Special days, breaks, menu — shared with the iOS app, served from Cloudflare. Format in `data/DATA_FORMAT.md`. `menu.json`, `events.json`, `day_type.json` are generated by Actions: never edit by hand |

## Vocabulary

- **Block**: one period of the day, lettered A–E. Students name their own
  blocks in Class settings ("A block" becomes "Chemistry").
- **Green day / White day**: the two alternating day types. A block can be a
  class on one and free on the other, so block preferences have `showOnGreen`
  / `showOnWhite`, `nameGreen` / `nameWhite`.
- **Day type**: which bell schedule applies today — regular, Wednesday,
  Friday, late start, ABDEC, no school. `scheduleService.loadBlocksForDate`
  decides, using `data/public/special_days.json` first and the school's
  Daily Bulletin as a fallback.
- **Lunch waves**: lunch is one block whose `subBlocks` are "1st Lunch" …
  "5th Lunch" with overlapping times. The popup shows them when the lunch row
  is expanded. `schedulePreferences.lunchPeriod` (1–5) exists in storage
  but nothing reads it yet.
- **CP**: the 20-minute block at the end of most days. Not a class.
- **Grades**: a block may carry `grades: [9, 10]`; the popup filters by the
  user's grade, derived from `graduationYear`.

## Build and check

```sh
cd chrome-extension
npm ci            # first time, or after package.json changes
npm run build     # must succeed; writes dist/
```

- Run the build yourself if you can. `dist/` is what Chrome loads, and the
  change is not real until it builds.
- `npx tsc --noEmit` reports ten pre-existing errors (`import.meta.env`
  typing, two in `scheduleService.ts`). They are not yours. Do not fix them
  in a PR about something else.
- `dist/` is git-ignored. Never commit it.
- There are no automated tests. Verification is: it builds, and it looks right.

### Looking at it without Chrome

If you have a browser you can drive (Playwright, or a `computerUse` tool), you
can preview the built popup: serve `dist/` over HTTP, open `popup.html`, and
before the page scripts run define a small `window.chrome` shim so the popup
does not crash — `chrome.runtime.sendMessage` should answer `getScheduleCache`
with the blocks from one of `public/schedule/*.json`, and `chrome.storage.sync`
can be an in-memory object. A screenshot of that is worth more to the person
you are working for than any description. Put it in the PR.

If you cannot run a browser, say so in the PR and point to the artifact below.

### How the person you are working for will see it

Every PR that touches `chrome-extension/` runs the **Build extension** Action,
which attaches the built `dist/` as a zip named `hilltoppers-extension-pr-<N>`.
The manifest in that zip is labelled `<version> (PR #<N>)` so it can be told
apart from the store copy. To try it they:

1. Open the PR → **Checks** → **Build extension** → **Artifacts** at the
   bottom, download the zip, unzip it.
2. Go to `chrome://extensions`, turn on **Developer mode**, click **Load
   unpacked**, pick the unzipped folder.
3. Turn off the store copy of Hilltoppers while testing.

Write those steps into the PR description. They may not know them.

## Conventions

- One branch per change, named for what it does. Do not bundle unrelated
  fixes.
- Any change under `chrome-extension/` bumps the patch version by 0.0.1 in
  **four** places: `manifest.json`, `package.json`, and twice in
  `package-lock.json` (top-level and `packages[""]`).
- A new entry in `manifest.json` `permissions` needs a one-sentence reason in
  the PR. The Chrome Web Store asks for it at review.
- Keep the UI as quiet as it is. Prefer changing an existing element over
  adding a new one. New text in the popup should be short and match the tone
  of what is already there.
- Comments explain *why*, not *what*. Some older comments are in Chinese; write
  new ones in English.
- Do not create explanatory `.md` files (`FIX_*.md`, `NOTES.md`, ...). If
  something needs documenting, it goes in an existing README or this file.
- Do not touch `ios/` unless asked. It needs Xcode and ships separately.
- Secrets: none are needed to build. Firebase config has committed defaults;
  see `SETUP.md` for the optional overrides. Never commit an `.env.local`.

## The pull request

Write it for the student, not for a reviewer. Three parts:

1. **What changed**, in one or two plain sentences. "Your lunch is now shown
   in bold in the lunch list, based on the lunch you pick in Class settings."
2. **How to try it**: the three artifact steps above.
3. **A screenshot**, if you could take one.

Mention the version number it bumps to. If you left something out or made a
judgment call, say so in a sentence — the person asking will not spot it in
the code.
